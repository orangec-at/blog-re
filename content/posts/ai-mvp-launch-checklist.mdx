AI 코딩 도구는 MVP를 빠르게 만들어줍니다. Cursor, v0, Bolt, ChatGPT를 잘 쓰면 며칠 만에 로그인, 대시보드, 폼, 결제 비슷한 흐름까지 만들 수 있습니다.

하지만 **돌아가는 MVP**와 **출시 가능한 제품**은 다릅니다.

<ArticleIntro
  thesis="출시 판단은 감이 아니라 boundary, failure state, deploy path를 확인하는 일입니다."
  points={[
    "데모에서는 잘 보이지 않던 문제가 실제 사용자, 실제 데이터, 실제 결제, 실제 권한 앞에서 드러납니다.",
    "비개발자 founder라면 ‘이 정도면 런칭해도 되는지’를 판단하기 어렵습니다.",
    "이 글은 formal security audit이 아니라, 공개 전 위험 신호를 빠르게 분류하기 위한 founder-friendly 체크리스트입니다.",
  ]}
/>

<ExpertInsight source="FixMyVibe field note">
  출시 전 진단은 기능 수보다 실패 경계와 데이터 경계를 먼저 봅니다. 가장 위험한 질문은 “기능이 있나?”가 아니라 “깨졌을 때 누구 데이터가 노출되는가?”입니다.
</ExpertInsight>

<RiskSection
  id="auth-session"
  index={1}
  title="Auth / session 경계가 명확한가"
  body="로그인이 된다고 해서 auth가 안전한 것은 아닙니다. Demo account 기준으로 화면이 잘 뜨는 데 집중하다 보면 실제 권한 경계가 흐려집니다."
  checks={[
    "사용자가 누구인지 검증하는가",
    "workspace/team 소속을 확인하는가",
    "record 접근 권한을 server-side에서 막는가",
    "session 만료 상태를 안전하게 처리하는가",
    "admin/user 권한 검증 위치가 명확한가",
  ]}
  question="User A가 User B의 private record를 읽거나 수정할 수 있는 경로가 정말 없는가?"
  noGo="UI에서 버튼을 숨겼으니 괜찮다가 유일한 권한 처리라면 아직 출시하면 안 됩니다."
/>

<RiskSection
  id="data-ownership"
  index={2}
  title="User / data ownership이 server-side에서 보장되는가"
  body="AI-generated code는 편의를 위해 데이터를 넓게 가져오는 경우가 있습니다. 화면에서는 자기 데이터만 보이는 것처럼 보여도, server-side query가 제대로 scoped 되어 있지 않으면 위험합니다."
  checks={[
    "DB query에 user/team/workspace ownership guard가 있는가",
    "public route와 private route의 반환 필드가 분리되어 있는가",
    "invite/link/share 기능에서 private 정보가 새지 않는가",
    "테스트 계정 2개로 교차 접근을 직접 확인했는가",
  ]}
  question="private data query는 항상 authenticated user/team/workspace로 제한되는가?"
  noGo="URL의 ID를 바꿨을 때 다른 사용자의 record가 열릴 가능성이 있으면 public launch는 멈춰야 합니다."
/>

<RiskSection
  id="secrets"
  index={3}
  title="Secret / API key가 노출되지 않는가"
  body="MVP를 빠르게 만들 때 가장 흔한 위험 중 하나가 secret 처리입니다. Next.js, Supabase, Firebase, Stripe, OAuth provider를 섞어 쓰면 어떤 값이 client bundle에 노출되는지 확인해야 합니다."
  checks={[
    ".env가 repo에 commit되지 않았는가",
    "server-only secret이 client component에 전달되지 않는가",
    "NEXT_PUBLIC_ 변수에 민감한 값이 들어가지 않았는가",
    "OAuth token이 log에 찍히지 않는가",
    "webhook secret, API key, service role key가 분리되어 있는가",
  ]}
  question="repo, browser bundle, log, screenshot을 누군가 봤을 때 노출되면 안 되는 key/token이 있는가?"
  noGo="service role key나 provider token이 browser에서 보일 수 있다면 출시 전에 반드시 막아야 합니다."
/>

<MiniCaseStudy
  title="Private beta 전에 발견한 권한 누수"
  problem="Demo account에서는 문제 없어 보였지만, 테스트 계정 2개로 교차 접근을 시도하자 private record 조회 가능성이 드러났습니다."
  outcome="Public launch 전에 P0 risk를 제거하고, 이후 수정 기준을 ‘UI 버튼 숨김’이 아니라 server-side ownership guard로 바꿨습니다."
  stats={["2 test accounts", "1 P0 risk removed", "48h stabilization"]}
/>

<RiskSection
  id="failure-states"
  index={4}
  title="Loading / error / empty / success state가 있는가"
  body="데모는 happy path만 보여줘도 됩니다. 제품은 실패 상태까지 설명해야 합니다. 사용자는 실패했을 때도 무엇이 일어났고 다음에 무엇을 해야 하는지 알아야 합니다."
  checks={[
    "loading state가 보이는가",
    "error message가 action-oriented한가",
    "empty state가 다음 행동을 안내하는가",
    "success state가 실제 DB/API 성공 이후에만 보이는가",
    "retry 또는 contact/support 경로가 있는가",
  ]}
  question="core flow가 실패했을 때 사용자는 무슨 일이 일어났는지, 다음에 무엇을 해야 하는지 알 수 있는가?"
  noGo="실패했는데 화면은 성공처럼 보이거나, 아무 반응 없이 멈춘다면 아직 제품이라고 보기 어렵습니다."
/>

<RiskSection
  id="validation"
  index={5}
  title="Server-side validation이 있는가"
  body="Client-side validation은 UX를 좋게 만듭니다. 하지만 제품을 지키는 것은 server-side validation입니다. 잘못된 payload가 DB까지 도달하는지 반드시 확인해야 합니다."
  checks={[
    "API route/server action에서 schema validation을 하는가",
    "required field, enum, date, amount, email, URL을 server-side에서 검증하는가",
    "user 권한과 input validation이 같은 boundary에서 확인되는가",
    "중복 요청, double submit, replay에 대한 최소 방어가 있는가",
  ]}
  question="잘못된 input, unauthorized input, malformed payload가 DB까지 도달할 수 있는가?"
  noGo="브라우저 devtools나 curl로 잘못된 payload를 보냈을 때 DB에 저장된다면 출시 전 수정이 필요합니다."
/>

<RiskSection
  id="deploy-path"
  index={6}
  title="Build / deploy / smoke test / rollback 경로가 있는가"
  body="로컬에서 돌아가는 앱이 곧 출시 가능한 앱은 아닙니다. MVP가 출시 준비가 되려면 install, check, build, preview, smoke test, rollback 경로가 반복 가능해야 합니다."
  checks={[
    "pnpm check, pnpm build 같은 검증 명령이 문서화되어 있는가",
    "production build가 local/CI에서 재현되는가",
    "핵심 route를 smoke test 했는가",
    "Vercel/hosting preview와 production 차이를 알고 있는가",
    "rollback이 dashboard 감으로만 남아 있지 않은가",
  ]}
  question="오늘 배포가 깨지면 어떻게 감지하고, 어떻게 마지막 정상 상태로 돌아갈 것인가?"
  noGo="내 컴퓨터에서는 되는데요 상태라면 공개 트래픽을 받기 전에 deploy path부터 정리해야 합니다."
/>

<RiskSection
  id="handoff"
  index={7}
  title="다음 개발자가 안전하게 이어받을 수 있는가"
  body="AI-built MVP는 처음 만든 사람에게는 익숙해 보여도, 다음 개발자에게는 위험할 수 있습니다. Logic이 UI에 숨어 있거나 API access가 각 화면에 흩어져 있으면 유지보수 비용이 빠르게 커집니다."
  checks={[
    "core flow를 설명하는 짧은 architecture note가 있는가",
    "수정 전후 실행해야 할 검증 명령이 있는가",
    "product-critical logic이 어디 있는지 찾을 수 있는가",
    "AI가 만든 중복 코드를 그대로 방치하지 않았는가",
  ]}
  question="다른 개발자가 core flow를 찾고, 고치고, 검증하는 데 얼마나 걸릴까?"
  noGo="만든 사람도 어디서 고쳐야 하는지 모르겠다고 느낀다면, 지금은 기능 추가보다 구조 파악이 먼저입니다."
/>
