AI 코딩 도구를 쓰면 아이디어에서 데모까지 가는 시간이 확 줄어듭니다. Cursor, Lovable, Bolt, v0, Replit, Supabase 조합이면 로그인 화면, 대시보드, 폼, 결제 버튼까지 생각보다 빨리 나옵니다.

문제는 그 다음입니다.

"돌아가는 앱"과 "출시 가능한 앱"은 다릅니다. 데모에서는 한 명의 테스트 계정, 깨끗한 데이터, 좋은 네트워크, 정상 결제만 봅니다. 실제 사용자는 session이 만료되고, 같은 버튼을 두 번 누르고, 권한이 다른 계정으로 URL을 열고, 결제 실패 뒤에 다시 들어옵니다.

AI는 prototype speed를 줍니다. 하지만 product responsibility까지 대신해주지는 않습니다.

## 1. Happy path가 아니라 실제 사용자 시나리오를 보세요

데모는 보통 가장 좋은 길만 보여줍니다. 새 계정으로 가입하고, 샘플 데이터를 넣고, 저장 버튼을 누르면 성공 메시지가 뜹니다. 그 정도면 investor demo나 내부 공유에는 충분할 수 있습니다.

출시는 다릅니다. 실제 사용자는 더 지저분한 상태로 들어옵니다.

  noGo="성공 path만 확인했고 실패 상태가 비어 있다면 public launch 전에 최소한 core flow부터 다시 봐야 합니다."

여기서 중요한 건 모든 edge case를 완벽히 막는 게 아닙니다. 첫 출시 전에 최소한 "실패했는데 성공처럼 보이는" 상태를 없애는 것입니다. 사용자가 돈을 냈는데 권한이 열리지 않거나, 저장이 실패했는데 완료처럼 보이면 신뢰가 바로 깨집니다.

## 2. 로그인만 보지 말고 auth/session 경계를 보세요

로그인 화면이 있다고 해서 auth가 끝난 것은 아닙니다. AI가 만든 MVP에서는 UI에서 버튼을 숨기는 방식으로 권한을 처리한 것처럼 보이는 경우가 있습니다. 하지만 사용자는 UI만 거치지 않습니다. URL을 직접 열 수도 있고, API route나 server action이 잘못된 요청을 받을 수도 있습니다.

<RiskSection
  id="auth-session"
  index={2}
  title="Auth와 session 경계가 server-side에서 확인되는가"
  body="로그인은 현관문입니다. 출시 전에는 현관문뿐 아니라 각 방의 잠금장치도 봐야 합니다."
  checks={[
    "로그인한 사용자가 누구인지 server-side에서 다시 확인하는가",
    "admin/user, owner/member, workspace/team role이 분리되어 있는가",
    "session 만료, 로그아웃, 계정 삭제 상태가 안전하게 처리되는가",
    "보호 route가 UI redirect에만 의존하지 않는가",

  ]}

  noGo="버튼을 숨기는 것이 유일한 권한 처리라면 아직 출시하면 안 됩니다."
/>

권한은 화면에서 예쁘게 숨기는 문제가 아닙니다. 서버, DB, API 경계에서 막혀야 합니다.

## 3. 데이터 소유권과 RLS를 직접 확인하세요

AI로 만든 앱에서 가장 위험한 순간은 "내 화면에는 내 데이터만 보인다"고 느낄 때입니다. 화면에서는 맞아 보여도 query가 넓게 열려 있으면 다른 사용자의 record가 섞일 수 있습니다.

Supabase를 쓴다면 RLS(Row Level Security)를 켰는지, policy가 너무 넓지 않은지, 테스트 계정 두 개로 교차 접근을 확인했는지 봐야 합니다.

<RiskSection
  id="data-ownership"
  index={3}
  title="User/data ownership이 DB 또는 API 경계에서 보장되는가"
  body="Login은 앞문이고, data ownership은 방마다 붙은 잠금장치입니다. 공개 전에는 User A가 User B의 데이터를 볼 수 없는지 직접 확인해야 합니다."
  checks={[
    "User A와 User B 테스트 계정을 따로 만들어 교차 접근을 시도했는가",
    "record 조회/수정/삭제 query가 user_id, team_id, workspace_id로 제한되는가",
    "Supabase RLS policy가 enabled 상태이고 public-safe table과 private table이 분리되어 있는가",
    "share link, invite link, public page가 private field를 반환하지 않는가",
    "권한 검사가 frontend state가 아니라 DB/API/server action에 있는가",
  ]}
  question="URL의 ID를 바꾸거나 다른 계정으로 같은 요청을 보내도 private record가 열리지 않는가?"
  noGo="다른 사용자의 record를 읽거나 수정할 가능성이 있으면 public launch는 멈춰야 합니다."
/>

이 부분은 숫자나 공포로 설득할 필요가 없습니다. 단순합니다. 실제 사용자 데이터가 들어오기 전에 소유권 경계를 증명해야 합니다.

## 4. Secrets와 server-only boundary를 확인하세요

빠른 MVP에서는 client/server 경계가 흐려지기 쉽습니다. 결제, OAuth, DB, 이메일, AI API를 붙이다 보면 key와 token이 어디까지 전달되는지 놓칩니다.

<RiskSection
  id="secrets"
  index={4}
  title="Secret/API key가 browser, repo, log에 노출되지 않는가"
  body="기능이 정상 작동해도 secret이 노출되어 있으면 출시 준비가 된 것이 아닙니다. 특히 service-role key, Stripe secret key, OAuth token, provider API key는 frontend bundle과 log에서 분리해야 합니다."
  checks={[
    ".env, credential file, service key가 repo에 commit되지 않았는가",
    "NEXT_PUBLIC_ 또는 client component로 민감한 값이 전달되지 않는가",
    "server-only action과 client component의 책임이 분리되어 있는가",
    "webhook secret, Stripe secret, Supabase service-role key가 runtime 환경에만 있는가",
    "error log, analytics event, screenshot에 token이나 개인정보가 찍히지 않는가",
    "유출 가능성을 발견했을 때 rotation plan이 있는가",
  ]}
  question="브라우저 bundle, GitHub repo, runtime log를 봤을 때 노출되면 안 되는 값이 있는가?"
  noGo="service-role key나 provider token이 browser에서 보일 수 있다면 출시 전에 반드시 막아야 합니다."
/>

실수 자체보다 더 위험한 건 "어디에 노출됐는지 모르는 상태"입니다. 출시 전에는 최소한 secret의 위치와 책임 경계를 한 번은 정리해야 합니다.

## 5. Checkout 성공이 결제 시스템 완성은 아닙니다

결제 버튼이 눌리고 성공 페이지가 뜬다고 해서 billing flow가 끝난 것은 아닙니다. 실제 서비스에서는 결제 성공보다 그 이후의 상태 관리가 더 중요할 때가 많습니다.

  checks={[

    "결제는 실패했는데 premium 권한이 남는 경로가 없는가",
    "중복 webhook이나 늦게 도착한 event가 잘못된 상태를 만들지 않는가",

  ]}

  noGo="결제 실패, 환불, 취소 뒤에도 유료 권한이 남거나 반대로 결제 성공 후 접근이 막히면 출시 전 수정이 필요합니다."
/>

첫 유료 사용자를 받을 생각이라면 이 항목은 뒤로 미루기 어렵습니다. 결제는 UX 문제가 아니라 신뢰와 운영의 문제입니다.

## 6. 배포 버튼보다 복구 경로를 먼저 확인하세요

Vercel, Netlify, Supabase, Firebase 같은 도구는 배포를 쉽게 만들어줍니다. 그래서 더 위험할 때가 있습니다. 버튼 한 번으로 배포할 수 있으면, 버튼 한 번으로 망가뜨릴 수도 있습니다.

  checks={[

    "DB backup과 restore 경로를 현재 risk 수준에 맞게 확인했는가",

  ]}
  question="오늘 배포가 깨지면 누가 알아차리고, 무엇을 보고, 어디로 되돌릴 것인가?"
  noGo="내 컴퓨터에서는 되는데 production에서 왜 깨졌는지 모르는 상태라면 공개 트래픽을 받기 전에 복구 경로부터 정리해야 합니다."
/>

출시 전 체크리스트에는 deploy command만 있으면 부족합니다. "깨졌을 때 돌아오는 길"이 같이 있어야 합니다.

## 7. 다음 개발자가 이어받을 수 있는지 확인하세요

AI-built MVP는 처음 만든 사람에게는 익숙해 보입니다. 하지만 다음 개발자가 들어오면 다른 문제가 보입니다. business logic이 UI 안에 숨어 있고, API 호출이 여러 component에 흩어져 있고, 같은 validation이 세 곳에 복사되어 있으면 작은 수정도 위험해집니다.

  checks={[
    "새 개발자가 local에서 프로젝트를 실행하는 방법을 알 수 있는가",

    "auth, data, payment, deployment 책임 경계가 코드에서 찾을 수 있는가",
    "중복 generated component와 임시 prompt-driven code가 정리되어 있는가",

  ]}
  question="다른 개발자가 오늘 들어와서 가장 중요한 flow를 찾고, 고치고, 검증하는 데 얼마나 걸릴까?"
  noGo="만든 사람도 어디서 고쳐야 하는지 모르겠다면 지금은 기능 추가보다 구조 파악이 먼저입니다."
/>

좋은 MVP는 완벽한 코드가 아닙니다. 그래도 다음 사람이 이어받을 수 있어야 합니다. 특히 첫 고객, 첫 결제, 첫 운영 이슈가 생기면 handoff 가능성은 곧 생존 가능성입니다.

## 리빌드부터 시작하지 말고 risk table부터 만드세요

출시 전 불안이 생기면 두 가지 극단으로 가기 쉽습니다. "일단 내자" 또는 "전부 다시 만들자"입니다. 둘 다 비쌀 수 있습니다.

더 안전한 첫 단계는 risk table입니다.
